## 一、竞品定位与本项目的坐标

先厘清一件事：本项目不是"又一个 Hexo 主题"，它是**带数据库的动态自托管博客**（SSR/ISR + 管理后台 + 评论），
技术坐标介于 **Astro（现代前端 DX）** 与 **Halo（国产动态 CMS）** 之间。因此竞品对比要分两类看：

| 竞品 | 类型 | 技术栈 | 上手难度 | SEO | 动态能力 | 与本项目关系 |
|---|---|---|---|---|---|---|
| **Hexo** | 静态生成器 | Node.js | ⭐ 最易（中文生态最全） | 插件式 | 无（需第三方评论） | 主要被替代对象 |
| **Hugo** | 静态生成器 | Go | 中等 | 优秀 | 无 | 构建速度标杆 |
| **Astro** | 现代静态/混合 | Node + 组件岛 | 较易 | 优秀（零 JS 默认） | 可选 | **最直接的正面竞品** |
| **Halo** | 动态 CMS | Java + SpringBoot | 低 | 优秀 | 完整（后台/评论/插件） | **技术栈最近的对标** |
| **WordPress** | 全能 CMS | PHP | 低 | 插件生态最强 | 完整 | 功能上限参照系 |
| **Ghost** | 内容平台 | Node.js | 低 | 原生 SEO | 完整 + Newsletter | 订阅/会员参照系 |
| **Obsidian Publish** | 数字花园 | — | 低 | 一般 | 无 | 本项目"数字花园"的直接对标 |

**关键判断**：本项目在"自建 + 可控 + 现代技术栈"这个象限里有真实价值，
但**功能完成度尚未达到 Halo/WordPress 这类动态 CMS 的基线**，而这正是博主迁移时会对比的。

## 三、缺失功能清单（按可行动性排序）

### P0 — 强烈建议尽快补齐（高影响 / 中低成本）

| # | 功能 | 对标 | 缺失影响 | 成本 | 建议方案 |
|---|---|---|---|---|---|
| 1 | **中文全文检索** | Halo / WP | 文章一多就搜不到东西，技术博客最常用入口失效 | 中 | `search.py` 已预留替换点。推荐 **Meilisearch**（自带中文分词、轻量、Docker 一行起）；轻量替代用 PostgreSQL `pg_trgm` + `similarity()` 排序 |
| 2 | **图片灯箱 + 懒加载** | 所有主题标配 | 技术文章截图看不清，长文首屏慢 | 低 | `medium-zoom`（~2KB，零依赖）做灯箱；`<img loading="lazy">` + Next.js `<Image>` 做懒加载与自动 WebP |
| 3 | **HTTPS** | 所有 | 不仅是安全：SEO 降权，且 `navigator.clipboard` 等安全上下文 API 全部不可用（已引发复制按钮故障） | 低 | 已有 `ssl.conf.example`，Let's Encrypt + certbot 容器即可 |
| 4 | **草稿自动保存** | Halo / WP | 编辑器崩了/误关标签页 = 几小时白写 | 低 | localStorage 定时快照（30s）+ 重新进入时提示"发现未保存草稿，是否恢复" |
| 5 | **阅读进度条** | 主题标配 | 长文无位置感 | 极低 | 顶部 2px 进度条，滚动监听；现代浏览器可直接用 CSS `scroll-driven animations` 零 JS |

## 四、差异化优势：已有且竞品少有，建议强化

这几项是本项目**真正的护城河**，多数竞品（尤其 Hexo/Hugo 主题）不具备，应在 about 页与 README 中主动叙事：

| 优势 | 竞品情况 | 强化建议 |
|---|---|---|
| **数字花园（双向链接 + 力导向图谱）** | 仅 Obsidian Publish / 少数 Astro 主题有，静态生成器基本缺失 | ① 图谱支持按分类筛选与节点聚类 ② 增加"未链接的孤岛文章"提示，引导补充内链 ③ `/garden` 独立页补 SEO 元数据 |
| **Ctrl/⌘+K 终端彩蛋** | 极客向，几乎无同类 | ① 扩展命令（`search <关键词>`、`goto <slug>`、`tags`）② 首次访问引导已做，可增加"输入 help 探索"的常驻提示 |
| **动态 OG 分享卡片** | 竞品多为静态图或插件生成 | 已优于多数竞品，保持；可增加分类色系与作者头像 |
| **反信息流的产品定位** | 与所有"增长导向"平台相反 | **建议强化为品牌叙事**：about 页已写"没有点赞、没有推荐算法、没有信息流"，这是很清晰的立场，可作为对外传播的核心差异点 |

> ⚠️ **明确不建议做**：点赞、推荐算法、信息流、会员付费墙。
> 这与 `about/page.tsx` 中已声明的产品立场直接冲突，加了反而稀释差异化。

## 六、一句话结论

> 本项目的**技术底子与特色功能（数字花园 / 终端彩蛋 / 动态 OG）已经超出同体量个人博客的平均水平**，
> 但卡在"从能用到好用"的最后一公里：搜索太弱、图片体验缺失、HTTPS 缺位、内容没有迁移路径。
> 补齐 P0 五项后，整体完成度即可对标 Halo 这类国产动态 CMS 的基线，
> 而差异化功能则是它有别于 Hexo/Hugo 主题站的关键理由。

### 关键取舍说明

1. **检索没上 Meilisearch，选了 pg_trgm + 中文分词**
   Meilisearch 自带中文分词，但要新增一个常驻容器与一条「写文章→同步索引」的链路，
   对单节点个人博客是明显的运维负担。pg_trgm 的三元组是**按字符**切的，
   天然对无空格语言友好（这与 `tsvector` 完全不同——后者会把整句中文当成一个 token），
   配合自建分词（整句 + 二元组）即可覆盖绝大多数检索场景，且零新增服务。
   后续真要升级，只需替换 `services/search.py` 的词元生成与查询构造，接口契约不变。

2. **两阶段召回**：先用「主词 AND」精确召回，零结果再放宽到「含二元组 OR」。
   避免噪声二元组让精确查询永远落空，也避免长中文查询一上来就零结果。

3. **阅读进度条默认走 CSS scroll-driven animations**，由合成器线程驱动；
   老浏览器降级到 rAF + scroll 监听（组件内特性探测）。长文快速滚动时主线程零开销。

4. **草稿只落 localStorage，不自动提交后端**：写了一半的内容不该在服务端留下痕迹，
   也不该污染文章列表；1.5s 防抖 + 30s 强制落盘，最坏只丢 30 秒。

5. **HTTPS 留在服务器侧执行**：证书签发、端口放行、`.env` 的 `SITE_URL` 切换
   都需要真实环境，脚本已把这些步骤固化并自带校验，跑一次即可。
