## 一、执行摘要

本轮测试覆盖 16 条前端路由、20+ 个后端接口、3 类特色功能（OG 卡片 / 数字花园 / 终端彩蛋）、上传与鉴权链路、SEO 产物与部署配置。

**功能面整体完成度较高**：文章列表、详情、分类、标签、归档、搜索、评论、后台增删改、限流、数字花园图谱接口均按预期工作，响应时间优秀（首页 TTFB 约 40ms），gzip 已启用，API 文档与 `.env`/`.git` 等敏感路径均已关闭。

**但安全与配置层面存在致命缺陷**：生产环境仍在沿用仓库默认凭据与默认 JWT 签名密钥，且登录接口无任何失败限流。三者叠加意味着**任何人在数秒内即可完全接管该站点**——这不是理论风险，本次测试已实际取得管理员令牌并完成建分类、读全量评论（含访客 IP）等操作。

测试过程中产生的全部数据（6 条测试评论、2 个测试媒体文件、1 个测试分类）**已在报告出具前通过管理接口清理完毕**，生产库未遗留脏数据。

## 三、P0 致命缺陷详情

### BUG-01 生产沿用默认管理员口令

- **现象**：使用仓库 `.env.example` 中的默认凭据可直接登录生产后台。
- **复现**：

```bash
curl -X POST http://111.231.98.59/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"admin12345"}'
```

- **实际结果**：`HTTP 200`，返回 `access_token` 与 `refresh_token`。
- **影响证明**：持该令牌成功创建分类（`POST /api/v1/categories` → 201）、读取全量后台评论（`GET /api/v1/comments`，响应中包含**访客 IP 地址**与邮箱）。
- **根因**：`backend/app/core/config.py:70` 定义 `ADMIN_PASSWORD: str = "admin12345"`，部署时未覆盖。
- **修复方案**：
  1. 立即在服务器 `.env` 中设置强口令（≥16 位，含大小写数字符号），并 `docker compose exec backend python scripts/init_admin.py` 重置。
  2. 代码层面：启动时校验 `SECRET_KEY`/`JWT_SECRET`/`ADMIN_PASSWORD` 若仍为默认值则**直接拒绝启动**（fail-fast），从机制上杜绝"忘记改"。

```python
# backend/app/core/config.py
FORBIDDEN_DEFAULTS = {"change-me-in-production", "change-me-jwt", "admin", "admin12345"}

@model_validator(mode="after")
def _reject_insecure_defaults(self):
    if not self.DEBUG:
        for name in ("SECRET_KEY", "JWT_SECRET", "ADMIN_PASSWORD"):
            if getattr(self, name) in FORBIDDEN_DEFAULTS:
                raise ValueError(f"{name} 仍为默认值，生产环境必须修改")
    return self
```

### BUG-02 生产 JWT 签名密钥为默认值

- **现象**：生产签发的 JWT 可用公开默认值 `change-me-jwt` 验签通过。
- **验证过程**：取登录返回的 `refresh_token`，分别用 `change-me-jwt` 与 `change-me-in-production` 计算 HS256 签名比对：

```
payload: {'sub': 'ac2915f7-12ce-4da8-8bd5-2c5366617122', 'exp': 1788897176, 'type': 'refresh'}
  用 'change-me-jwt' 验签:            ✅ 匹配（生产仍在用默认密钥！）
  用 'change-me-in-production' 验签:   不匹配
```

- **影响**：攻击者无需知道口令，可**离线伪造任意用户（含管理员）的令牌**，完全绕过登录。危害性高于 BUG-01——即便改了口令也无济于事。
- **根因**：`backend/app/core/config.py:25` `JWT_SECRET: str = "change-me-jwt"`，部署未覆盖。
- **修复方案**：
  1. 生成高熵密钥：`openssl rand -hex 32`，写入 `.env` 的 `SECRET_KEY` 与 `JWT_SECRET`（两者使用不同值）。
  2. 重启后**强制所有已签发令牌失效**（当前 access token 为 24 字符不透明串，需确认存储位置一并清理）。
  3. 接入上条 fail-fast 校验。

### BUG-03 登录接口无失败限流

- **现象**：连续 12 次错误密码，全部返回 `401`，无 `429`、无账号锁定、无延迟递增。
- **证据**：

```
第1次: 401  第2次: 401  ...  第12次: 401   （全程无 429/423）
```

- **影响**：与 BUG-01/02 叠加，攻击者可无限次枚举口令；即便修复默认口令，弱口令仍会被爆破命中。
- **根因（代码复核后修正）**：初版报告判断为"登录接口未接入限流"，走查代码后发现
  `auth.py` **其实写了限流**，但第 50 行的失败计数调用 `hit(f"login-fail:{ip}", ...)`
  **丢弃了返回值、从不判断是否超限**——等于装了锁却从不落锁。
  而真正生效的只有 `login:{ip}` 的总量计数（阈值 15 次/10 分钟），
  12 次尝试刚好没触顶，所以全部放行。这类"写了防护但没接线"的缺陷比"完全没写"更隐蔽。

- **修复方案**（已实施，见第十一节）：失败计数既写也读，并叠加三层防护——
  总量限流 → 失败锁定（IP 维度和 IP+账号维度）→ 时序均衡（账号不存在时也做一次 bcrypt
  校验，避免响应时间差异泄露账号是否存在）。

## 四、P1 高危缺陷详情

### BUG-04 / BUG-05 文件上传：存储型 XSS 与魔数校验绕过

- **现象一（XSS）**：上传含脚本的 SVG 成功，且以同源 `image/svg+xml` 返回，脚本会被浏览器执行。

```bash
# 上传
curl -X POST -H "Authorization: Bearer $TOKEN" \
  -F "file=@evil.svg;type=image/svg+xml" \
  http://111.231.98.59/api/v1/media/upload
# → 201 {"url":"/media/15d7f4cb2c4a4330af24c8616516a165.svg"}

# 访问
curl -I http://111.231.98.59/media/15d7f4cb2c4a4330af24c8616516a165.svg
# → Content-Type: image/svg+xml
# → 内容: <svg ...><script>alert(document.domain)</script></svg>
```

  由于站点**无 CSP**（见 BUG-07），直接访问该 URL 即触发脚本执行 → **同源存储型 XSS**，可窃取管理员令牌、劫持后台会话。

- **现象二（魔数绕过）**：构造以 PNG 魔数开头、实际内容为 SVG 的 polyglot 文件，同样上传成功。
- **根因**（`backend/app/api/v1/endpoints/media.py:27-96`）：
  - `ALLOWED_MIME` 允许 `image/svg+xml`，但魔数校验分支**只覆盖 png/jpg/gif**，SVG / WebP / AVIF 完全无校验。
  - 魔数校验仅比对文件头若干字节，不校验文件整体结构与类型一致性。
- **修复方案**：
  1. **最简单有效**：从 `ALLOWED_MIME` 中移除 `svg`；若业务确需 SVG，上传时用 `defusedxml` + 白名单清洗（剔除 `<script>`、`on*` 事件属性、`foreignObject`、外部实体），并以 `Content-Disposition: attachment` 或独立域名（如 `media.example.com`）提供，切断同源。
  2. 引入真实类型识别（如 `python-magic` / `pillow` 解码验证），替代"比对文件头"的弱校验——用 `PIL.Image.open()` 尝试解码，失败即拒绝。
  3. 所有媒体响应强制 `X-Content-Type-Options: nosniff`。
  4. nginx 层对 `/media/` 增加 `add_header Content-Security-Policy "default-src 'none'; style-src 'unsafe-inline'; sandbox";`。

### BUG-06 全站 HTTP 明文传输

- **现象**：`https://111.231.98.59/` 无响应（`000`），站点仅提供 HTTP；登录口令、JWT 均以明文在网络传输，局域网/链路中间人可直接截取。
- **影响**：结合 BUG-02，攻击者甚至无需伪造令牌，抓包即可拿到真实凭据。
- **修复方案**：
  1. 参照 `nginx/ssl.conf.example` 接入 Let's Encrypt（`make` 中增加 `cert` 目标，容器内用 certbot 申请）。
  2. nginx 增加 80 → 443 全量重定向，并开启 HSTS：`add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;`。
  3. 后端 Cookie（若使用）加 `Secure; HttpOnly; SameSite=Lax`。

### BUG-07 安全响应头全面缺失

- **现象**：首页响应头仅有 `Server / Date / Content-Type / Vary / Cache-Control`，以下全部缺失：

| 响应头 | 作用 | 当前 |
|---|---|---|
| `Content-Security-Policy` | 阻断 XSS 执行 | ❌ 缺失 |
| `X-Content-Type-Options: nosniff` | 阻断 MIME 嗅探 | ❌ 缺失 |
| `X-Frame-Options` / `frame-ancestors` | 防点击劫持 | ❌ 缺失 |
| `Strict-Transport-Security` | 强制 HTTPS | ❌ 缺失 |
| `Referrer-Policy` | 控制来源泄露 | ❌ 缺失 |
| `Permissions-Policy` | 限制敏感 API | ❌ 缺失 |

- **修复方案**（`nginx/default.conf`，注意 `add_header` 在子块会覆盖父块，需逐块添加或置于 `server` 层并配合 `always`）：

```nginx
add_header X-Content-Type-Options "nosniff" always;
add_header X-Frame-Options "SAMEORIGIN" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
add_header Permissions-Policy "geolocation=(), microphone=(), camera=()" always;
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;  # 启用 HTTPS 后
add_header Content-Security-Policy "default-src 'self'; script-src 'self' 'unsafe-inline' 'unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data: https:; font-src 'self' data:; connect-src 'self'; frame-ancestors 'self'; base-uri 'self'; object-src 'none'" always;
```

> Next.js 需 `'unsafe-inline'`/`'unsafe-eval'`（框架内联脚本与 HMR 依赖）。上线后应逐步收敛为 nonce 方案，并对 `/media/` 单独下发 `default-src 'none'; sandbox`。

### BUG-08 `SITE_URL` 未配置，SEO 产物全部指向 localhost

- **现象**：RSS、canonical、og:url 中站点地址均为 `http://localhost`。

```xml
<!-- /api/v1/feed.xml -->
<link>http://localhost</link>
<atom:link href="http://localhost/feed.xml" rel="self" .../>
```
```html
<!-- 首页 -->
<meta property="og:url" content="http://localhost"/>
```

- **影响**：搜索引擎收录的规范化 URL、社交平台分享预览全部指向 localhost，SEO 实质失效；OG 分享卡片分享出去指向不可达地址。
- **根因**：`.env` 中 `SITE_URL` 未设置为 `http://111.231.98.59`（或正式域名）。
- **修复方案**：在服务器 `.env` 中设置 `SITE_URL=http://111.231.98.59`（配置 HTTPS 后改为 `https://`），重启 backend 与 frontend；随后在 Google Search Console / 百度站长平台重新提交 sitemap。

## 五、P2 功能缺陷详情

### BUG-09 `/feed.xml`、`/sitemap.xml` 返回 404

- **现象**：

```
GET /feed.xml     → 404  Content-Type: application/json  {"detail":"Not Found"}
GET /sitemap.xml  → 404  Content-Type: application/json
GET /api/v1/feed.xml    → 200 (application/rss+xml)
GET /api/v1/sitemap.xml → 200 (application/xml)
```

- **根因**：后端 `meta.py` 的路由挂在 `api_router` 下，实际路径带 `/api/v1` 前缀；而 `nginx/default.conf:53-63` 用 `location = /feed.xml`（精确匹配，优先级最高）把请求转发到 `http://backend_upstream/feed.xml`，路径不匹配 → 后端 404。同时该精确匹配**抢先于** Next.js 的 rewrite，`/feed.xml` 永远到不了前端兜底。
- **修复方案**（二选一，推荐 A）：
  - **A. 改 nginx 转发路径**（改动最小）：

```nginx
location = /feed.xml {
    proxy_pass http://backend_upstream/api/v1/feed.xml;
    proxy_set_header Host $host;
}
location = /sitemap.xml {
    proxy_pass http://backend_upstream/api/v1/sitemap.xml;
    proxy_set_header Host $host;
}
```

  - **B. 后端补根路由**：在 `app/main.py` 中直接挂载 `@app.get("/feed.xml")`，使根路径可用（更利于 SEO 与第三方订阅器兼容）。
- **回归验证**：`curl -I http://111.231.98.59/feed.xml` 应返回 `200` 且 `Content-Type: application/rss+xml`。

### BUG-10 `/posts` 列表页 404

- **现象**：`GET /posts` → 404；但 `src/app/posts/[slug]` 详情页正常（200）。
- **根因**：`frontend/src/app/posts/` 目录下**缺少 `page.tsx`**，仅有 `[slug]` 子路由。
- **修复方案**：明确产品定义——若首页即文章列表，则删除 `posts/` 空目录并确保全站无 `/posts` 链接；若需独立列表页，补充 `src/app/posts/page.tsx`（复用首页列表组件），并在 `sitemap.ts` 中登记。

### BUG-11 评论限流阈值过紧

- **现象**：连续提交评论，第 5 次起返回 `429 评论太频繁了，请稍后再试`。
- **影响**：正常用户短时间内回复 4 条以上即被拒，体验受损；且限流按 IP 全局计数，同一 NAT 出口（公司/校园网）会互相牵连。
- **修复方案**：核对 `.env` 中 `COMMENT_*` 阈值，建议放宽至"同一 IP 每 5 分钟 10 条 + 同一 IP 对同一文章每 10 分钟 3 条"的组合策略，并对已登录管理员豁免。

### BUG-12 搜索空关键词返回 422

- **现象**：`/api/v1/search?q=` 与 `/api/v1/search`（无 q）均返回 `422`。
- **建议**：空关键词应返回 `200` + 空结果集（或最近文章），前端已有空态 UI 时体验更一致；若坚持校验，前端需在提交前拦截并给出提示。

### BUG-13 后台鉴权仅存在于客户端

- **现象**：未登录访问 `/admin`、`/admin/posts`、`/admin/comments` 均返回 `200`（HTML 骨架），跳转由客户端 `AuthGuard` 完成。
- **风险**：服务端渲染阶段会先下发页面骨架与 JS bundle，**管理端代码结构对未登录访客可见**；一旦客户端守卫逻辑被绕过或 token 校验有缺陷，将直接失守。
- **修复方案**：在 `src/app/admin/(panel)/layout.tsx` 中做**服务端守卫**——读取 cookie 中的 token，无效则 `redirect('/admin/login')`，使未授权请求在服务端即终止，不返回任何管理端内容。

### BUG-14 数据面过于单薄

- **现象**：全站仅 1 篇文章、1 条评论；`/api/v1/garden/graph` 返回单节点 0 条边，`/api/v1/posts/{slug}/links` 出链与反链均为空。
- **影响**：数字花园力导向图、双向链接、分页、搜索高亮、评论树状回复等功能**缺乏有效验证数据**，无法判定真实场景下的正确性与性能。
- **建议**：执行 `make seed` 灌入示例数据（建议 ≥30 篇文章、含 `[[双向链接]]`、多级评论回复），完成一轮完整回归后再清空。

### 11.2 关键实现说明

**① fail-fast 而非仅仅"提示"**
最初考虑在启动时打印警告，但警告会被日志淹没。改为 `APP_ENV=production` 时直接抛异常终止启动——
实测效果：

```
生产环境安全校验未通过，已拒绝启动：
  - SECRET_KEY 仍为默认占位值，请执行 `openssl rand -hex 32` 生成后写入 .env
  - JWT_SECRET 仍为默认占位值，请执行 `openssl rand -hex 32` 生成后写入 .env
  - ADMIN_PASSWORD 仍为默认口令，生产环境必须修改
  - SITE_URL 指向 localhost，会导致 RSS / Sitemap / OG 卡片全部失效
```

**② 上传校验：从"比对文件头"到"真实解码"**
魔数比对只能证明前几个字节合法，polyglot 文件（合法头 + 恶意载荷）轻易绕过。
改为 Pillow 完整解码并比对解码出的格式，实测三类攻击载荷：

| 载荷 | 结果 |
|---|---|
| PNG 文件头 + `<script>` 载荷 | ❌ 拦截（"文件内容与声明类型不符，或文件已损坏"） |
| 真实 JPEG 声明为 PNG | ❌ 拦截（"文件真实类型为 JPEG，与声明的 png 不一致"） |
| 合法 PNG | ✅ 放行 |
| SVG 含 script/onload/foreignObject/外部 href | ✅ 净化为 `<svg><circle …/></svg>`，危险内容全部剔除、合法图形保留 |

**③ 服务端鉴权的实现约束**
Server Component 读不到 localStorage，因此 `setAuthToken` 在写 localStorage 的同时写入
同名 cookie（`blog_token`）。注意：**未启用 HTTPS 时不能加 `Secure` 标志**，否则浏览器会
直接丢弃该 cookie——代码中已加注释，待 BUG-06 修复后补上。

**④ Nginx `add_header` 继承陷阱**
Nginx 中一旦某个 location 内出现 `add_header`，**server 层的所有 `add_header` 会被全部丢弃**。
因此凡是有自定义 `add_header` 的 location（`/media/`、`/_next/static/`）都重新 include 了
安全头片段，否则这些路径下会毫无防护。这一点已写入配置文件注释。
