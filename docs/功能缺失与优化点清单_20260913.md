## 一、本次新确认的问题（共 12 个，含修复过程中新增的 BUG-14）

这一节是本次审计相对 2026-09-11 缺口分析**新增**的发现，均已实证。

### BUG-01（P0）前端 sitemap 静默失效：一条文章都不收录

| 项 | 内容 |
|---|---|
| **位置** | `frontend/src/app/sitemap.ts:22` |
| **取证** | ① `sitemap.ts` 请求 `page_size: 500`；② 实读后端 OpenAPI：`/api/v1/posts` 的 `page_size` **maximum = 200**（`deps.py:28` 的 `le=settings.MAX_PAGE_SIZE`）；③ 500 > 200 → **422**；④ `lib/api.ts:89` `if (!res.ok) return null` —— **静默吞掉错误**；⑤ `sitemap.ts:26` `(data?.items \|\| [])` → 空数组 |
| **后果** | 该 sitemap **只输出 7 条静态路由，零篇文章**，且不报错、不报警 |
| **是否已暴露** | 生产环境**暂时未暴露**——因 `nginx/default.conf:73` 把 `/sitemap.xml` 直接转给后端 `/api/v1/sitemap.xml`，前端这份被遮蔽。但这是「双份真源 + 静默失败」，任一路径改动即暴露，且前端那份**现在等于完全不可用** |
| **修法** | 与 BUG-02 一并处理（二选一），不要两份并存 |

### BUG-02（P0）存在两份 sitemap 真源，且口径不一致

| 维度 | 后端 `services/feed.py::build_sitemap` | 前端 `app/sitemap.ts` |
|---|---|---|
| 静态路由 | **4 条**：`/`、`/archive`、`/tags`、`/garden` | **7 条**：多 `/posts`、`/categories`、`/about` |
| 文章取数 | 全量（无 limit，正确） | `page_size=500` → 实际 0 条（见 BUG-01） |
| lastmod 口径 | `published_at` 优先，回退 `updated_at` | `updated_at` 优先 |
| 生效路径 | **生产生效**（nginx 转发） | 被遮蔽 |

> 同一份内容有两个实现、两套口径、两种结果。**这是典型的「双份真相」**，与模型中 `posts.view_count` / `post_stats.view_count` 是同一类问题。

### BUG-03（P0）SEO 缓存失效链路是断的

| 项 | 内容 |
|---|---|
| **取证** | ① `services/seo.py:81` 定义了 `refresh_seo_cache()`，全仓 **grep 零调用点** → **死代码**；② `notify_seo_changed()`（`seo.py:90`）在 `posts.py` 的 **4 处**（建/改/发布/删）被调用，但它只是 `publish(INVALIDATE_CHANNEL, "changed")`；③ 全仓**没有任何订阅者**（无 worker、无后台任务） |
| **后果** | 启用 Redis 时，`sitemap.xml` / `feed.xml` 命中缓存后**最多滞后 3600 秒**（`SEO_CACHE_TTL=3600`）才反映新文章。新文章发布后一小时内外链抓取、阅读器订阅都看不到 |
| **未暴露原因** | 未配 `REDIS_URL` 时 `cache_get` 恒返回 `None`，每次都实时渲染 → 无 Redis 反而正常 |
| **修法** | 二选一：① 发文时**同步**失效缓存（成本最低，单机够用）；② 补一个真正的订阅者进程 |

### BUG-04（P1）后端 sitemap 缺 3 个重要落地页

`build_sitemap` 只输出 `/`、`/archive`、`/tags`、`/garden`，**缺 `/posts`（文章列表主入口）、`/categories`（分类列表）、`/about`**。
另外 **tags 详情页（`/tags/<slug>`）与 categories 详情页（`/categories/<slug>`）两份实现都未收录** —— 这两类是文章之外最重要的聚合落地页，不收录等于放弃它们的搜索排名。

### BUG-05（P1）RSS 只输出摘要，无全文

- `build_feed`（`feed.py:31-43`）每篇只有 `<title>/<link>/<guid>/<pubDate>/<description>`，`description` 填的是 `summary`，**无 `<content:encoded>` 全文**。
- 技术博客读者的普遍预期是**全文 RSS**（在阅读器内读完）；只有摘要会迫使读者跳站，削弱 RSS 的实际价值。
- 同时未声明 `xmlns:content` 命名空间，加全文需一并补。
- `render_feed` 硬编码 `.limit(50)`（`seo.py:34`），无分页 / 无"更多条数"控制。

### BUG-06（P2）RSS 的 `author` 字段是空转字段

`seo.py:43` 计算了 `"author": p.author.display_name if p.author else settings.SITE_AUTHOR`，但 `build_feed` **从头到尾没读过 `it['author']`** → RSS 里既无 `<author>` 也无 `dc:creator`。
与 `post_stats` 空转、`media.width/height` 恒为 0 属同一类「写了不读」负债。

### BUG-07（P2）`datetime.utcnow()` 已废弃

`feed.py:13`、`feed.py:27` 使用 `datetime.utcnow()`。Python 3.12+ 已标记 deprecated，且返回**无时区**的朴素对象，却拼上硬编码的 `+0000` —— 将来若服务器时区非 UTC 会静默产生错误时间。应改 `datetime.now(timezone.utc)`。

### BUG-08（P1）评论表单根本没有邮箱字段 —— 通知功能的硬前置

| 项 | 内容 |
|---|---|
| **取证** | `CommentSection.tsx:57-82` 表单只有 **昵称 / 个人站点 / 正文** 三个输入，**无 email** |
| **后果** | 即使补齐 `comments.notify_on_reply` / `email_verified` / `unsubscribe_token` 三个字段，**也收集不到邮箱** → 回复通知访客的功能无法落地 |
| **意义** | 这比「给 comments 补字段」更靠前：**先决定邮箱采集口径（必填？选填？如何告知用途？如何合规存储？），再谈补字段**。当前 `author_email` 已在库中且**后台接口原样返回**（`comments.py:203`），合规风险已经存在 |
| **修法** | 与「邮箱脱敏」一并作为一次改动：补邮箱输入 + 用途说明 + 后台掩码输出 |

### BUG-09（P1）嵌套回复不显示「回复 @某某」

`CommentItem` 只渲染 `comment.content`（`CommentSection.tsx:133`），**没有任何"回复给谁"的标识**。深度 ≥2 的折叠/缩进场景下，读者无法判断这条在回复谁。根因是 `comments` 缺 `reply_to_name` —— 与模型缺口分析的结论一致，但此处给出的是**用户体验层的具体后果**。

### BUG-10（P1）后台 4 处使用浏览器原生 `window.confirm`

| 位置 | 操作 |
|---|---|
| `PostsTable.tsx:159` | 删除文章 |
| `CommentsPanel.tsx:155` | 删除评论 |
| `MediaPanel.tsx:200` | 删除图片 |
| `TaxonomyPanel.tsx:123` | 删除标签/分类 |

原生弹窗：**无法套用站点主题**（在三主题体系里尤其突兀）、不可自定义按钮文案、**阻止主线程**、移动端样式不可控、无法为不可逆操作提供更强的确认（如要求输入标题首字）。
删除文章**不可撤销**（无回收站、物理删除、评论与双向链接被 CASCADE 带走），却只用一个原生两字按钮确认 —— **风险等级与确认强度不匹配**。

### BUG-11（P2）编辑器使用 `document.getElementById` 而非 ref

`MarkdownEditor.tsx:57`、`77` 通过 `document.getElementById("md-editor")` 操作输入框。在分屏/预览模式下 DOM 会随 `mode` 变化卸载重建，**依赖全局 id 的取值可能拿到 `null` 或旧节点**（代码里已用 `if (!el) return` 兜底，但表现为"工具栏点了没反应"，属难复现的偶发问题）。应改为 `useRef`。

### BUG-14（P1）`noindex` 从未被 sitemap 尊重 —— 本轮修复过程中新发现

| 项 | 内容 |
|---|---|
| **取证** | 第一阶段刚加了 `posts.noindex`（「已发布但不希望被收录」，如临时公告、内部文档），但 `services/seo.py::render_sitemap` 的查询只有 `status == PUBLISHED`，**从未读取 `noindex`** |
| **后果** | 一篇文章同时被 `<meta name="robots" content="noindex">` 和 `sitemap.xml` 声明：**对搜索引擎是矛盾信号**。声明不收录却又主动提交收录，轻则被忽略，重则影响对站点其他信号的信任度 |
| **修法** | `render_sitemap` 加 `Post.noindex.is_(False)` 过滤 |

> 这个缺陷有意思的地方在于：它是**在修另一个 bug 时才暴露的**。单独看 `noindex`（写入路径完整、详情页 metadata 正确）和 sitemap（能正常输出）都没有问题，只有把两条链路对上才发现不一致——这也说明「字段加了不等于链路通了」。

### 3.2 体验与交互优化

| 编号 | 优化点 | 现状 | 影响 | 建议 |
|---|---|---|---|---|
| OPT-01 | **后台删除确认** | 4 处原生 `window.confirm`（BUG-10） | 主题割裂、风险与确认强度不匹配 | 统一为站内 Modal；不可逆操作要求输入标题首字 |
| OPT-02 | **后台批量操作** | 零批量能力（G-41） | 审核高峰期逐条点击 | 表格加多选 + 批量通过/驳回/删除 |
| OPT-03 | **后台列表搜索** | 无搜索框 | 文章数上来后定位困难 | 列表页加关键词 + 状态 + 时间范围筛选 |
| OPT-04 | **编辑器预览与线上渲染不一致** | 预览走前端 `react-markdown` + `rehype-highlight`；线上走后端自建 `services/markdown.py`（Pygments、TOC、图片尺寸注入） | **所见非所得**：代码高亮配色、目录、图片尺寸都可能不同 | 让预览调用后端渲染接口，或至少对齐插件与配色 |

### 8.2 一个刻意的「不做」

**没有顺手加 `notify_on_reply` / `email_verified` / `unsubscribe_token`**，尽管《模型与功能缺口分析》建议「一次把表设计到位」。

理由：本站**当前没有任何发信能力**（无 SMTP 配置、无 Subscriber / EmailLog 表）。此时若加 `notify_on_reply`，前端就会出现「回复时邮件通知我」的勾选框，而系统永远不会发信——**这比没有该字段更糟，它是对读者的空承诺**。

这直接对应本清单 DEBT-10 那条原则：**新增字段前需确认有读取方**。故迁移 `0004` 只加了 `reply_to_name`（当轮即有写入方与读取方）。通知类字段等通知功能真正落地时随其一起迁移。（邮箱本身无需迁移：`comments.author_email` 早已存在，此前缺的只是前端采集入口。）

## 九、第二轮修复记录：令牌吊销（G-40）

**验证结果：后端 `pytest` 118 passed（原 94 + 新增 24）/ `ruff` clean / 前端 `next build` 通过（25 条路由，新增 `/admin/account`）。**

### 9.1 修复前的真实形态（先取证，再动手）

清单一度把 G-40 记作「refresh token 吊销缺失」——这个说法**低估了它**。实测三条证据：

| 证据 | 命令 / 位置 | 结果 |
|---|---|---|
| 没有改密码端点 | `grep -rn "password" app/api/v1/endpoints/auth.py` | 只有 `login` 里用 `verify_password`，**没有任何写入 `password_hash` 的地方** |
| 没有 logout 端点 | 同上 | `/auth` 下只有 `login` / `refresh` / `me` 三条路由（`app.openapi()` 实测） |
| refresh 不校验任何代次 | `auth.py::refresh` | 只判 `user is None or not user.is_active`，随后**直接签发新令牌对** |

三条合起来得到的结论比「缺失一个功能」严重得多：

> **密码泄露之后，改密码对攻击者毫无影响。**
> 旧 `access_token` 能用到自然过期（`ACCESS_TOKEN_EXPIRE=30` 分钟），
> 旧 `refresh_token`（`REFRESH_TOKEN_EXPIRE=720` 分钟）可以**无限续期**。
> 而用户在 UI 上根本找不到改密码的入口——**他连做那个无效动作的机会都没有。**

这是安全问题里最坏的一类：用户以为存在一个处置手段，实际不存在。

### 9.2 落地方案

| 环节 | 做法 | 位置 |
|---|---|---|
| 数据 | `users` 加 `token_version`（`Integer`，NOT NULL，`server_default='0'`） | 迁移 `0005`、`models/user.py` |
| 签发 | `create_access_token(subject, version)` / `create_refresh_token(subject, version)` 把代次写进 `ver` 声明。**`version` 设为必填位置参数**——漏传会静默落成 0，而 0 恰好是「未改过密码」的合法值，这种失效不报错，只让吊销形同虚设 | `core/security.py` |
| 校验 | 三个入口全部比对：`get_current_user`（强制鉴权）、`optional_user`（可选鉴权）、`refresh`（刷新）。吊销提示文案独立为 `REVOKED_DETAIL="凭证已失效，请重新登录"`，与「已过期」区分开 | `api/deps.py`、`endpoints/auth.py` |
| 触发器 | 新增 `POST /auth/change-password`：校验当前密码 → 拒绝新旧相同 → 更新哈希 → `token_version += 1` → **返回按新代次签发的令牌对** | `endpoints/auth.py` |
| 入口 | 新增后台「账号安全」页 `/admin/account` + 侧栏入口；成功后立即用新 token 覆盖本地凭证 | `app/admin/(panel)/account/`、`AdminSidebar.tsx` |

**为什么这一轮必须连「触发器」一起做**：本清单 DEBT-10 的原则是「新增字段前需确认有读取方」。
`token_version` 如果只加列不加改密码端点，就是第二份 `post_stats`——一份没人写、也没人读的真相。
所以列、校验、触发器、UI 入口是**一次交付**，缺任一环则该环之前的努力全部无意义。

### 9.3 三个刻意的设计选择

**① 吊销粒度是「整用户」而不是「单令牌」。**
单枚令牌级吊销需要引入 denylist（Redis 存 `jti`）或服务端会话表，还要配套设计「Redis 挂了怎么办」。
本站需要处理的真实场景只有「密码泄露 / 设备丢失后改密码」——**把全部设备踢下线正是期望行为**，
而作者本人重新登录的成本约等于零。用一列整数换取这个能力是划算的一侧。
补偿手段：改密码接口返回新令牌对，**当前设备不被打断**。

**② 老 token 缺 `ver` 声明按 0 处理，而不是视为无效。**
升级上线那一刻，线上在用的 token 都不带该声明。若视为无效，等于**强制全体重新登录**——
安全能力上线不该以清空全部会话为代价。按 0 处理后，它们与存量用户（默认 0）仍然匹配；
一旦改密码把值推到 1，这些老 token 立即失效。
（对照：解码失败返回 `None` / 空 dict 属于「根本不是 JWT」，走拒绝分支，不享受这个宽恕。）

**③ 不做 logout 端点。**
只能用 `token_version` 实现 logout 的话，等价于「点一次退出登录，把所有设备都踢掉」——
这是用户不会预期的行为。单设备登出属于客户端行为（清本地凭证），当前前端已如此实现
（`AdminSidebar.tsx::logout`）。**需求是单设备登出、而实现只能全设备登出时，宁可不做。**

### 9.4 回归测试（24 个）与验证纪律

新增 `tests/test_token_revocation.py`，按「缺一个吊销就是摆设」的思路覆盖三个环节：

| 环节 | 用例 |
|---|---|
| ① 签发 | access / refresh 都带上代次；**缺 `ver` 的老 token 读作 0**（锁住升级平滑这个决策）；`None` 归一为 0；`"abc"`/`True`/`dict`/`None`/`list` 一律拒绝 |
| ② 校验 | 新代次通过；**落后一格即 401**；**超前也拒绝**（只判「小于」会在回滚场景放行"未来"令牌）；`optional_user` 被吊销时返回 `None`；**旧 refresh 不能换取新 access** |
| ③ 触发器 | 改密码后库里代次真的 +1；旧 access / 旧 refresh 双双失效；新令牌立刻可用；新密码能登录、旧密码不能；当前密码错 → 400 且**不改动任何状态**；新旧相同 → 400；新密码长度下限（12 位）；**存量行原始 INSERT 回填为 0 而非报错**（对应迁移的 `server_default`） |

**验证纪律（证明测试不是空跑）**：写完后把三处比对**临时注释掉**跑了一次，确认**正好 5 条变红**，
