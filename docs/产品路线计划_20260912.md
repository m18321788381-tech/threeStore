## 二、瓶颈判断：为什么是这三件事

我把候选缺口全部过了一遍，剔除「可以做但不该现在做」的项后，剩下三个**结构性瓶颈**。

### 瓶颈 A（最高优先）：可信度缺口——「已完成」尚未被生产环境证明

| 事实 | 影响 |
|---|---|
| 3 个迁移从未在真实 PostgreSQL 上执行过（本机无 Docker） | 一致性测试只能静态逼近列/索引/唯一性/默认值，**覆盖不了 PG 执行期问题**（锁等待、类型强转、`server_default` 回填行为）。上线日才发现问题 = 全站不可用 |
| HTTPS 脚本从未实跑，当前站点仍是 HTTP | ① SEO 降权；② `navigator.clipboard` 等安全上下文 API 不可用（**历史上已实际引发复制按钮故障**，见 `1d31c5a`、`c7dd99f`） |
| 站点承载在 4 容器编排上（db / backend / frontend / nginx），无独立 worker，Redis 单列在 `docker-compose.redis.yml` | 备份/恢复脚本存在但未做过一次真实恢复演练；限流状态依赖 Redis，若未启用则防爆破能力存疑 |

> **这一项不排第一，后面所有「已完成」都只是声明而非证明。** 成本很低（一次 staging 部署 + 一次恢复演练），收益是整条后续路线的前提。

### 瓶颈 B：地基层缺口——配置与内容形态锁死在代码里

- **没有 SiteSetting**：站点标题、描述、备案号、社交链接、GSC/Bing 验证码、每页条数、评论开关**全部散落在环境变量与代码常量**。改一项要改 `.env` **并重建前端**（README 已明确 `SITE_URL` 需重建）。
- **没有 Page**：`about` 是硬编码路由，无法自建「书单 / 项目 / 友链」页。
- **没有 Friend**：友链页无表可依。

> 这三张表是**所有「后台可配置」功能的落脚点**。不补，后面每一个功能都要各自造一套配置读取方式。

### 瓶颈 C：观测与反馈闭环缺口——无法判断「有没有人读」

- **没有 PageView（访问事件）**：当前只有累计计数（`posts.view_count`），无时间维度、无来源、无路径。`views_last_7d` 曾因此造假数据，已按「宁可不出字段也不出假数字」原则删除。
- **直接后果（必须承认的约束）**：**本次路线图的优先级评分只能是 PM 判断，不是数据驱动**——因为还没有任何真实读者行为数据。这也是 PageView 必须前置到第 2 期、而不是「有空再做」的理由。
- **评论无法形成对话**：`comments` 无 `notify_on_reply` / `email_verified` / `unsubscribe_token` / `reply_to_name`，访客被回复不会收到通知，且通知时**不知道发给谁**。
- **读者读后即走**：无 Newsletter/Subscriber/EmailLog——这是个人博客拉回访最有效的手段（Ghost 的核心能力）。

### 显式排后（不是遗漏）

| 项 | 为什么现在不做 |
|---|---|
| 对象存储抽象（S3/OSS） | 单节点自托管，本地卷不是瓶颈；提前抽象 = 为不存在的问题付复杂度成本 |
| 多语言 i18n | 需先确认读者构成，属战略选择而非功能补齐 |
| 多用户/角色、全文替换为 Meilisearch | 单作者已足够；检索替换点已预留（`services/search.py` 接口契约不变） |

## 三、目标与指标

### 3.1 北极星指标

> **North Star：7 日回访读者数（7 日内独立访客中访问 ≥ 2 次的人数）**

为什么**不用 PV/UV 当北极星**：`about/page.tsx` 已公开声明「没有点赞、没有推荐算法、没有信息流」。以 PV 为北极星会立刻把产品拖回「追流量」的动机结构，与技术博客的忠实读者价值错位。回访读者数是**唯一同时满足「反映真实价值」与「不违背产品立场」**的指标。

### 3.2 支撑指标分层（对照 AARRR，按本项目形态改写）

| 层 | 指标 | 为什么是它 | 数据来源 | 现状 |
|---|---|---|---|---|
| 获客 Acquisition | 自然搜索落地会话数、被外部站点引用数 | 技术博客的主要入口是搜索；外链是内容质量的客观投票 | PageView.referrer + 站外统计 | ❌ 无数据源 |
| 激活 Activation | 深度阅读会话率（停留 ≥ 60s）、特色功能采用率（garden / ⌘K / search 使用占比） | 激活 = 完成一次有意义的阅读；特色功能采用率验证护城河是否被真实使用 | PageView + 前端埋点 | ❌ 无数据源 |
| 留存 Retention | 7 日回访率、订阅转化率（订阅者 / 回访读者）、评论互动率（有评论文章占比） | 核心层，直接支撑北极星 | Subscriber + comments | ❌ 无数据源 |
| 收入 Revenue | **本项目明确不做付费墙** → 替换为：内容资产增长率（月新增文章数）、单月运维成本 | 无商业化，收入层换为「资产与成本」两头 | 后台统计 + 云账单 | 部分可算 |
| 推荐 Referral | 外链被引用数、分享链接点击 | 反信息流立场下，推荐靠内容自发传播 | PageView.referrer | ❌ 无数据源 |

> ⚠️ **全部目标值均为待校准假设**：因为当前**没有任何真实基线数据**。第 2 期 PageView 上线并积累 ≥ 4 周数据后，本节所有目标值需用真实基线重设。现在给出数字化目标（如「回访率 ≥ 25%」）等于编造。

### 3.3 反向指标（Guardrail Metrics）

做增长动作时**必须同时盯住、一旦恶化就该回滚**的指标：

| 反向指标 | 恶化含义 | 阈值触发动作 |
|---|---|---|
| 会话中位停留时长 | 内容质量被稀释（为量牺牲质） | 停止内容扩张，回到深度选题 |
| 评论审核积压量 | 通知/反垃圾能力跟不上互动增长 | 先补审核留痕与 spam 评分，再放开通知 |
| RSS 订阅退订数 | 推送节奏打扰读者 | 降低推送频率，改为摘要式 |
| 搜索被索引页数 | noindex 被误用或 robots 出错 | 立即核查 SEO 覆盖字段写入路径 |
| 后台 5xx 错误率 | 上线新功能引入回归 | 门禁：`pytest` 全绿 + `next build` 通过才允许合并 |

## 五、优先级评分（RICE，相对评分）

**评分口径说明**（重要，否则容易误读）：

- **Reach 是相对值**（0–100，表示每 100 个受影响的会话/操作中占几份），不是绝对人数——因为**当前没有真实流量数据**。全部数值为 PM 判断，第 2 期 PageView 上线后须重算。
- 对**作者侧**功能（版本历史、孤儿清理等），Reach 按「后台会话占比」记——单作者产品里作者是唯一操作员，其 Reach 事实上是 100%，但影响面只落在运营效率上，故用低 Impact 表达。
- Effort 单位为「人周」，含实现 + 测试 + 迁移。

**RICE 结论与人工修正**（框架是起点不是终点）：

1. **RM-3.3（邮箱脱敏）RICE 极高但成本极低**，被评分表意外顶到前列——确认为**合规风险项，应立即执行**，不必等到第 3 期。已从第 3 期提前为「随时可做」。
2. **RM-3.6（导入导出）RICE 最低**（5），但它是**外部博主采纳本产品的最大障碍**——Reach 低是因为「潜在迁移者」当前确实是少数，属**战略性投入而非流量投入**。因此保留在第 3 期而不砍掉，但允许在资源紧张时后置，并明确记录这是**有意识的取舍**。
3. **RM-3.4（版本历史）Reach 仅 10** —— 但「误删不可回滚」是**不可逆损害**，属于 Kano 模型里的**基本需求（门槛）**：缺了会不满，有了不加分。对不可逆风险，RICE 的线性期望值模型天然低估，故按**风险规避逻辑**保留在 P1。
4. **RICE 未纳入依赖关系**：RM-2.1/2.4/2.5 分数中等，但它们是 RM-3.x 全体的前置。**分数排序 ≠ 执行顺序**，实际执行顺序由第六节依赖决定。

## 十、一句话结论

> 三石笔记的功能层已经站上「对标 Halo 基线」的位置，**真正的短板不在功能，而在三件更靠前的事**：
> ① 全站还没被生产环境证明过一次（迁移与 HTTPS 均未实跑）；
> ② 配置与内容形态仍锁死在代码里（SiteSetting / Page 缺失）；
> ③ 没有访问事件表，导致连「有没有人读」都不知道——**这也是本路线图所有优先级数字只能是 PM 判断的原因**。
>
> 因此执行顺序是明确的：**先用一周证明它能跑（阶段 0），再用三周补地基并装上眼睛（第 2 期），最后用四周把读者留住（第 3 期）**。
> 阶段 0 的成本极低而收益是「整条路线的前提」，是当前**性价比最高的投入**。
