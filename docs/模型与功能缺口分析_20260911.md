# 三石笔记 · 数据模型与功能缺口分析

| 项目 | 内容 |
|---|---|
| **分析对象** | 三石笔记（Next.js 15 + FastAPI + PostgreSQL 16 自托管博客） |
| **分析日期** | 2026-09-11 |
| **方法** | 全量代码走查：8 张 ORM 模型 / 10 个端点模块 / 9 个 service / 2 个 Alembic 迁移 / 前端 51 个页面与组件逐项核对 |
| **前序文档** | 《竞品分析与功能缺口调研_20260909》（P0 五项已交付）、《功能测试报告_20260908》（17 项缺陷已修 16） |
| **结论** | 功能层的 P0 已补齐，但**模型层仍停在 MVP 快照**：3 处"空转资产"（写了不读 / 字段永不写入 / 僵尸列），1 处"双份真相"，12 类实体完全缺失——其中「站点设置」「自定义页面」「访问事件」三张是地基表，不补会持续卡住后续功能 |

---

## 一、结论摘要

四句话概括：

1. **3 处空转资产**：`post_stats` 表只写不读、`media.width/height` 声明了却永不写入、`post_stats.like_count` 是产品明确不做点赞后留下的僵尸字段。
2. **1 处双份真相**：`posts.view_count` 与 `post_stats.view_count` 同时维护，而前者才是所有读取路径的真源。
3. **缺 12 类实体**，其中 **SiteSetting / Page / PageView** 不补，后面的设置页、自定义页面、统计看板都无从谈起。
4. **顺带发现 3 个模型契约不一致**，其中一个（`prev/next.id` 返回 slug）是可直接定位的真 bug。

## 二、现有 8 张表逐表体检

### 2.1 posts — 主表，字段最全，但缺"运营级"字段

| 项 | 内容 |
|---|---|
| **现状** | title / slug / summary / content_md / content_html / toc / cover_url / status / view_count / reading_time / published_at |
| **问题 1** | `view_count` 与 `post_stats.view_count` **双份真相**（`posts.py:232-239` 同步双写），而读取路径全部走 `posts.view_count` |
| **问题 2** | 缺 `is_pinned` —— 评论表有 `is_pinned`（`comment.py:45`），文章表没有；`sort` 参数只支持 `newest/oldest/popular` |
| **问题 3** | 缺 SEO 覆盖字段：`canonical_url` / `noindex` / `meta_description`（现在只能复用 `summary`） |
| **问题 4** | 缺 `scheduled_at` —— `published_at` 只在状态切换时打当前时间戳（`posts.py:303、383`），无法定时发布 |
| **问题 5** | 缺软删除 `deleted_at` —— `delete_post` 物理删除，评论与双向链接被 CASCADE 一起带走，无回收站 |
| **建议** | 补 `is_pinned`（排序权重）、`scheduled_at`、`deleted_at`、`canonical_url`、`noindex`；`view_count` 的去留见 2.3 |

### 2.2 media — 有字段，但一半是空的

| 项 | 内容 |
|---|---|
| **现状** | filename / url / mime_type / size / **width / height** / uploader_id |
| **问题 1（硬）** | `width` / `height` **从未被写入**：`media.py:291-297` 构造 `Media()` 时只传 5 个字段，两列恒为 0 |
| **问题 2** | 无 `alt` / `caption` → 无障碍（a11y）与图片 SEO 双输 |
| **问题 3** | 无内容指纹 `content_hash` → 同一张图重复上传产生重复文件与重复记录 |
| **问题 4** | 与 posts **无任何关联** → 回答不了"这张图被哪篇文章引用"，删文后图片变孤儿，后台清理只能靠猜 |
| **影响** | 前端无法输出 `width`/`height` 属性 → 图片加载产生 **CLS（布局偏移）**；无法生成 `srcset` 做响应式；无法做孤儿文件清理 |
| **建议** | 上传时 Pillow **已经打开过图片**（`media.py:118` 的 `Image.open`），顺手取 `img.size` 即得，**零额外成本**；`alt` 由编辑器插入时填写；补 `content_hash` 做秒传去重 |

### 2.3 post_stats — 只写不读的"空转表"

| 项 | 内容 |
|---|---|
| **现状** | post_id（unique）/ view_count / like_count |
| **问题 1（硬）** | **全仓唯一写入点是 `posts.py:234-239`，没有任何读取点**。`serializers.py:38`、`posts.py:102`（popular 排序）、`stats.py:36`（总量汇总）全部读 `posts.view_count` |
| **问题 2** | 模型注释写的是"拆分表便于异步批量写"，但实现是**同步双写**，设计意图完全没有落地 |
| **问题 3** | **没有时间维度** → `stats.py:53` 的 `views_last_7d` 直接 `return int(total_views)`，代码里自己写了注释承认（"详见下方说明"，实际没有说明） |
| **问题 4** | `like_count` 是僵尸列：产品立场明确"没有点赞"（`about/page.tsx` 声明 + 竞品文档第 169 行"明确不建议做"） |
| **建议** | **二选一，不要维持现状**：① 删表 + 删 `posts.view_count` 之外的冗余；② 或升级为唯一真源 + 补日粒度表 `post_views_daily(post_id, date, count)`。推荐 ②，因为它是"7 日趋势/来源分布"唯一正解 |

### 2.4 comments — 能审核，但不能"对话"

| 项 | 内容 |
|---|---|
| **现状** | post_id / parent_id / author_name / author_email / author_site / content / ip / ua / status / is_pinned / is_author |
| **问题 1** | 无 `reply_to_name` 等被回复者信息 → 展示"回复 @某某"要额外 join，且**通知时不知道该发给谁** |
| **问题 2** | `author_email` 明文存储、**后台原样返回**（`comments.py:203`）、无脱敏 → 隐私合规风险 |
| **问题 3** | 无 `notify_on_reply` / `email_verified` / `unsubscribe_token` → 做回复通知与退订**必须先补字段**，否则要改两次表 |
| **问题 4** | 无审核留痕（`moderated_by` / `moderated_at`）、无 `spam_score` |
| **建议** | 补 `reply_to_name`、`notify_on_reply`、`email_verified`、`unsubscribe_token`、`moderated_at`；后台邮箱做掩码输出 |

### 2.5 post_links — 数字花园的护城河，但信息量太少

| 项 | 内容 |
|---|---|
| **现状** | source_post_id / target_post_id / created_at + 唯一索引 |
| **问题 1** | **没有锚文本与上下文** → 反链面板只能显示标题；而 Obsidian 的反链面板核心体验是**"引用它的那句话"** |
| **问题 2** | 无未解析链接记录 → 无法统计"站内有哪些 `[[xx]]` 待补"，竞品文档第 164 行提的"孤岛文章提示"**没有数据支撑** |
| **建议** | 补 `anchor_text` + `context`（前后各 N 字）；未解析的 `[[xx]]` 单独记录，支撑"待补内链"看板 |

### 2.6 tags / categories — 太素

| 表 | 问题 | 建议 |
|---|---|---|
| **tags** | 仅 name / slug；无 `description`、`color`/`icon`、`sort_order`；`post_count` 每次实时聚合 | 补 `description`、`color`、`sort_order`；量级上来后物化计数或缓存 |
| **categories** | 模型支持多级（`parent_id`），但架构文档 §7 自己写着"当前 UI 单级"；无 `sort_order` / `icon`；"未分类"靠 `category_id = NULL` 而非真实记录 → **分类页无法列出"未分类"这一组** | 补 `sort_order`、`icon`；或建一条真实的"未分类"记录做兜底 |

### 2.7 users — 单作者可接受，但令牌吊销是空的

| 项 | 内容 |
|---|---|
| **现状** | username / email / password_hash / display_name / avatar / bio / role / is_active / last_login_at |
| **问题 1** | 无 refresh token 版本号或吊销位 → `auth.py:131-147` 只校验签名与 `type`，**改密码/登出后旧的 refresh token 依然有效**，令牌吊销形同虚设 |
| **问题 2** | 无 `password_changed_at` |
| **问题 3** | 无审计表 —— 登录失败记录只活在 Redis 计数器里（`auth.py:104`），**谁在什么时候爆破过后台，事后无据可查** |
| **建议** | 补 `token_version`（JWT 里带版本校验）；新增 `AuditLog`（登录成功/失败、后台写操作） |

## 三、缺失实体清单（12 类）

| # | 实体 | 为什么必须补 | 被谁依赖 | 优先级 |
|---|---|---|---|---|
| 1 | **SiteSetting**（key-value） | 站点标题/描述/备案号/社交链接/GSC·Bing 验证码/每页条数/评论开关，现在**全在环境变量与代码常量里** → 改一项要改 `.env` 并**重建前端**（README:241 明确写了 SITE_URL 要重建前端） | 后台设置页、站点验证、备案展示 | **P0 地基** |

| 3 | **Friend**（友链） | 常见缺失。需站名/URL/头像/描述/状态/排序 | 友链页 | **P0** |
| 4 | **PageView**（访问事件） | 唯一能支撑"7 日趋势 / 来源分布 / 热门路径"的模型。当前**只有累计数**，趋势图无源可依 | 站点统计看板、趋势图 | **P0 地基** |
| 5 | **Redirect**（301 记录） | `update_post` 允许自由改 slug（`posts.py:330-339`），**旧链接立即 404，SEO 权重丢失且无补救路径** | slug 重命名自动 301 | **P1** |
| 6 | **PostRevision**（版本快照） | 误删/误改不可回滚（竞品文档 P2 第 14 项） | 版本历史、回滚 | P1 |

| 8 | **EmailLog**（发信记录） | 通知/订阅推送的可观测与重试基础 | 评论通知、订阅推送 | P1 |

| 11 | **AuditLog** | 后台写操作留痕，安全审计基础 | 安全审计 | P2 |
| 12 | **media ↔ post 关联** | 判断图片归属与孤儿，支撑清理与"文章附件" | 媒体库清理 | P2 |

## 八、一句话结论

> 功能层的 P0 已经补齐，**瓶颈已经从"功能缺失"转移到"模型债务"**：
> `post_stats` 空转、`media` 尺寸恒为 0、`views_last_7d` 造假数据，这三项都是"看起来有、实际没有"的隐性负债，
> 比明确缺失更危险——因为它们会让人误判系统能力。
> 建议第 1 期先把这三处清掉并补齐 posts/media 的字段，第 2 期再落地 **SiteSetting 这张地基表**，
> 之后所有"后台可配置"的功能才有落脚点。

### 关键取舍说明

1. **置顶只作用于列表页**，不改归档页与 RSS 的时序。理由：时间线的可信度比"置顶曝光"更重要，混在一起会让读者以为文章发布于置顶顺序对应的时间。

2. **图片尺寸在服务端渲染时注入，而不是前端脚本补**。前端补已经晚了——等脚本执行时布局已经跳动过一次，CLS 已被计入。因此拆成两步：后端 `render_post_content` 一次性查出该文用到的媒体的尺寸，渲染时写进 `<img width height>`；`media_meta` 是普通 dict，渲染函数保持纯函数，便于单测。

3. **`redirects` 不挂 posts 外键**。旧链接的价值恰在文章删除后依然存在（至少应给出明确响应而不是 404），挂 FK 会让记录随文章 CASCADE 一起消失，等于白记。

4. **重定向解析接口读路径带一次写入**（累加 `hit_count`）。这是刻意取舍：没有命中计数就永远无法判断某条重定向是否还有真实流量，也就永远不敢删它。用 SQL 原子自增避免并发丢计数，记录条数由"作者改过多少次 slug"决定，规模极小。

5. **`views_last_7d` 直接删掉，而不是"造"一个值**。该字段前端从未被使用，删除零破坏。真正的 7 日趋势需要访问事件表，划归第二期 PageView——在那之前宁可不出这个字段，也不出假数字。

6. **同图去重采用"复用物理文件 + 独立记录"**，并给删除端加了引用计数守卫。若只是复用文件而不守卫，删掉其中一条记录就会 unlink 掉其他记录仍在使用的文件。

### 10.2 一致性测试真抓到的三处漂移（均已修）

新写的迁移-模型一致性测试并非"写个测试图安心"——它在首次运行时就抓出三处**真实的代码不一致**：

| # | 漂移 | 危害 | 修法 |
|---|---|---|---|
| 1 | `posts.canonical_url`：模型 `Mapped[str]`(NOT NULL)，迁移写成 `nullable=True` | 模型与线上 DDL 不一致，autogenerate 反复报差异；且 NOT NULL 列的写入路径可能被误判为可空 | 迁移改为 `nullable=False` + `server_default=""` |
| 2 | `post_links`：模型靠列上 `index=True` 隐式生成 `ix_post_links_source_post_id`，迁移里叫 `ix_post_links_source`；且 `target_post_id` 上**叠了两条重复索引**（隐式一条 + 显式一条） | 索引名与线上不符；`target_post_id` 上多出一条完全冗余的索引，白占写入开销 | 全部改为显式 `Index(...)`，与 0001 逐字对齐，删掉重复项 |
| 3 | `posts.status`：模型声明 `index=True`（生成 `ix_posts_status`），但**迁移从未创建过该索引** | 模型描述的物理结构与线上不符；且该索引本就冗余（`ix_posts_status_published_at` 以 status 为最左前缀已完全覆盖） | 移除模型上的 `index=True` |

> 教训：这三处都是"照着模型改、忘了照迁移"或反过来的典型产物。**迁移是线上的物理真源，模型只是它的声明式投影**——一致性测试的价值就是不让两者悄悄分叉。

### 10.3 已知偏差与限制（如实列出）

1. **实际返回的是 308 而非 301**。`next/navigation` 的 `permanentRedirect()` 发出 HTTP 308（Permanent Redirect）。308 与 301 同为永久重定向，语义差别只在"是否保留请求方法"；对搜索引擎而言权重传递等价，Google 明确将 308 视同永久重定向。选择它是为了不改动 App Router 的标准写法（无需 middleware、无额外一跳）。**若要求字面上的 301**，需新增 `middleware.ts` 在路由前解析并返回 301，代价是每个 `/posts/*` 请求多一次后端查询。

2. **图片尺寸被固化进 `content_html` 缓存**。渲染在"保存文章"时执行并落库，因此若某张图**被同名替换**（删除旧记录后上传新图、尺寸不同），旧文章的缓存里仍是旧尺寸，需重新保存文章才会更新。属低频边界（正常上传会生成新文件名），第二期做「媒体变更时触发引用文章重渲染」时一并解决。

3. **在媒体库改 alt 不会立刻反映到已发布文章**。同上原因：`alt` 在保存文章时注入 `content_html`。`PATCH /media/{id}` 只更新媒体记录本身。

4. **`resolve_slug` 的原子自增未做并发验证**。SQLite 测试覆盖了语义（自增、计数），但 PG 下的并发行为未实测；实现上刻意用了 `UPDATE ... SET hit_count = hit_count + 1` 而非"读出来 +1 再写回"，正是为了避免并发丢计数。

5. **迁移未在真实 PostgreSQL 上执行过**。本机无 Docker，`alembic upgrade head` 无法实跑；一致性测试是从静态 DDL 层面逼近，能覆盖列/索引/唯一性/默认值，**不能**覆盖 PG 特有的执行期问题（如锁等待、类型强转）。部署前建议先在 staging 跑一次 `alembic upgrade head`（生产库为空表时风险极低，`server_default` 已保证存量行回填）。
